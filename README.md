# LogiVerse — 核心框架起点（从 LifeVerse 抽取）

这是从你的 LifeVerse 代码库里抽出来的**通用框架骨架**，不是完整系统——十几个游戏模块、课程/关卡管理这些教育平台专属的东西还没在这里面，那些是 Phase 1 之后要接的。

这份代码**实际跑过、验证过**：后端 `tsc --noEmit` 零错误、真的连数据库跑起来测过登入/建账号/单一会话；前端 `tsc -b` 零错误、`vite build` 真的把生产包打出来过。不是没测过的猜测代码。

## 目录结构

```
logiverse-starter/
├── backend/          Node/Express/TypeScript 后端
├── frontend/          React/Vite/TypeScript 前端
└── db-migrations/       三个 SQL 文件，依序执行
```

## 怎么跑起来

### 1. 数据库

```bash
createdb logiverse_dev
psql -d logiverse_dev -f db-migrations/00_core_schema_only.sql
psql -d logiverse_dev -f db-migrations/00b_seed_reference_data.sql
psql -d logiverse_dev -f db-migrations/001_education_roles_and_session_policy.sql
```

### 2. 后端

```bash
cd backend
cp .env.example .env   # 改 DATABASE_URL / JWT secrets
npm install
npm run dev             # http://localhost:4000
```

第一个账号要手动建（`/auth/users` 端点本身需要 OPERATOR/TEACHER 权限才能调用，鸡生蛋蛋生鸡）：

```sql
-- 先算一个 bcrypt hash（node -e "require('bcryptjs').hash('你的密码',12).then(console.log)"）
INSERT INTO auth.users (username, password_hash, status, registered_via)
VALUES ('你的IC号码', '算出来的hash', 'ACTIVE', 'BOOTSTRAP')
RETURNING id;

INSERT INTO rbac.user_roles (user_id, role_id)
SELECT '上面拿到的id', id FROM rbac.roles WHERE code='OPERATOR';
```

### 3. 前端

```bash
cd frontend
cp .env.example .env    # 设 VITE_API_URL=http://localhost:4000/api/v1
npm install
npm run dev              # http://localhost:5173
```

## 从 LifeVerse 拿掉了什么

`modules/lifeverse/*` 整个模块（动态/日记/开销/家庭/目标/通知/帖子/日程/社交/任务）——这是 LifeVerse 自己的个人生活记录功能，教育平台用不到。前端对应的 `pages/lifeverse/*` 也整批没带过来。

`modules/org/` 底下的 banner / committee / comms / events / files / finance / landing / meetings / membership / pages / projects 这些 controller 也没带——这些是社群经营功能（活动报名、财务记账、委员会管理、聊天频道），教育平台的"组织"只是"学校分校"这个简单概念，不需要这些。

**注意**：`db-migrations/00_core_schema_only.sql` 是整个 `org` schema 原样抽出来的，所以这些没用到的表（`org.events`、`org.finance` 等）其实还在数据库里，只是没有对应的 API 代码去动它们，不会造成问题，但如果你想要一个完全干净的 schema，之后可以手动把这些表 DROP 掉。

## Phase 2 再更新：界面统一改用 Tailwind

之前几个模块的引擎（`CountingGame`/`SpotDiffGame`/`FocusTapGame`/`MemoryGame`）都是直接从原本的独立 HTML 原型移植过来的，用的是内联 `style={{}}`——能跑，但跟应用其他部分（`CourseDesignerPage`、`AppLayout` 这些本来就用 Tailwind 写的）风格不统一，也没有吃到项目本来就有的深色模式配色（`index.css` 里定义的 `--primary`/`--muted` 这些 CSS 变量）。

这次全部改成 Tailwind class：
- 四个游戏引擎的渲染部分（状态提示、卡片、按钮）都改用 Tailwind，颜色语意化处理（答对绿色、答错红色都用 Tailwind 的 `emerald`/`red` 色阶，深色模式自动适配，不用另外写一套深色样式）
- `CourseDesignerPage.tsx` / `GradeTiersPage.tsx` 的表格从"能看"升级成"好看"——表格外面包一层圆角边框容器、表头用 `bg-muted/50` 区分、行 hover 有过渡效果，原本裸的 `<select>`/`<input type=number>` 现在跟设计系统的 `<Input>` 组件用同一套 class（边框、圆角、焦点环全部一致）
- 加关卡弹窗里，不同模块类型各自的参数区块现在包在一个 `bg-muted/40` 的卡片里，视觉上跟"关卡名称"这类主要字段区分开来

唯一保留内联样式的地方是两处 CSS Grid 的 `gridTemplateColumns`（专注力点数字的格子数、Memory的卡片列数）——这两个是运行时才知道数字的动态值，Tailwind 没办法用静态 class 表达，这是合理的例外，不是漏改。

验证方式：`tsc -b` + `vite build` 零错误，另外还检查了用三元表达式写的条件 class（比如"答对显示绿色、答错显示红色"这种）有没有被 Tailwind 的生产环境 purge 不小心清掉——写法上每个分支都是完整的 class 名称字符串（不是拼接出来的），purge 后逐一确认这些 class 真的还在最终的 CSS 文件里，不是那种会被 Tailwind 扫描器漏掉的动态拼接写法。

## Phase 2 再更新：游戏界面放大 + 找规律 + 应用题（鸡兔同笼/相遇问题）

**界面尺寸**：之前几个游戏的容器宽度写得偏保守（`max-w-md`=448px、`max-w-[420px]` 这些），跟"尽量跟着显示器体积"的要求不符。这次把 `LevelPlayerPage` 外层容器从 `max-w-4xl` 放宽到 `max-w-6xl`（1152px），每个游戏内部的容器也跟着放宽（点点数数/专注力/Memory 都到 `max-w-2xl`=672px，找不同直接用满 6xl），配合把图标、按钮、字体尺寸也按比例放大（比如点点数数的选项按钮从 padding `px-6 py-3.5` 放大到 `px-10 py-6`，图标从 `text-4xl` 放大到 `text-6xl sm:text-7xl`），不是单纯拉宽容器留白，是整体视觉元素都跟着放大。

**找规律**（`edu.pattern_configs`）：展示一段按规律排列的图案序列（AB/ABC/AAB/ABB/AABB 五种规律类型，可复选混合出题），让学生选出接下来该是什么。用 Node 跑了2000次随机测试验证规律生成逻辑（不同规律类型对应的"下一个该是什么"计算正确）。

**应用题**（`edu.word_problem_configs`）——这个模块设计成**一个 module_type 支持多种题型**，不是每种题型各自开一个模块，这跟最早那个独立原型（`word-problems-prototype.html`）混合六种题型的思路是一致的：
- **鸡兔同笼**：复用之前 Phase 0 验证过的反推生成法（先定鸡数兔数，算出头数腿数）
- **相遇问题**（新题型，之前没做过，这次是第一次设计）：两车从两地相向而行，给定距离和两车速度，求相遇时间（或反过来给定速度和时间求距离）。用 Node 跑了5000次随机测试验证"距离=时间×(速度1+速度2)"这个反推生成的正确性
- 两种题型可以在同一关**混合出题**（配置里的 `categories` 是个洗牌袋），课程设计者可以只选一种，也可以两种都选
- 支持选择题和键盘输入两种作答方式

| 等级 | 网格大小 | 最大高度 | 空格概率 |

## 应用题模块升级：鸡兔同笼 + 相遇问题改成可操作式互动

原本这两个题型是"读文字、选或输入一个数字"，现在换成"边操作边看结果、凑对了再交答案"——更贴近这两类题目本来该有的解题直觉，出题的数学逻辑完全没变（v1 已经验证过的生成算法照原样保留），只是把答题这一步从"选择/输入"换成"操作/验证"。

**鸡兔同笼**：往笼子里加鸡加兔（+/− 步进按钮），画面实时显示当前头数、腿数，跟题目给的目标数字对比，凑对了会打勾变绿。最后交的答案是"当前放了几只鸡/兔"，不是另外再输入一个数字——学生是靠试错调整凑出正确答案的，这是这题在学代数之前本来就该有的解法。

**相遇问题**：画面上两辆车分别在起点A、起点B，中间一条"路"。用一个滑杆控制——如果题目问"几小时后相遇"，滑杆拖的是时间，两车位置跟着实时移动，画面告诉你"还差几公里"或者"正好相遇了"；如果题目问"两地相距多少"，滑杆拖的是距离，车的位置固定在题目给的时间对应的位置，学生调整路的长度直到两车正好对上。两种问法用的是同一套"调整滑杆直到差距归零"机制，不是两套不同的UI。

**验证方式**：Node 跑了3000次随机测试，专门验证"滑杆调到正确答案那个数值时，两车之间的差距是不是精确等于0"——因为这个交互能不能用，直接取决于这个数学关系是否严丝合缝，不是"看起来差不多"就行。鸡兔同笼那边的头腿计算公式跟 v1 完全一样，没有变过。

后端这边完全没动——出题的 API、config 的资料结构都不变，只是前端把"答题"这一步重新设计了，所以另外做了回归测试确认原本存在的应用题关卡还是能正常抓到配置、正常玩。

- 班级：建立、列出（老师只看得到自己的班级——每个 handler 都先检查 `classes.teacher_id = 当前登入者`，这个模式跟家庭那边的 `guardian_relationships` 检查是同一个精神）
- 名单：**加的是已经存在的学生账号**（用IC查），不会新建账号——建账号是业者或家长的事，老师只是把已有的学生"拉"进自己的班级
- 作业：把一个 `course_level` 分配给整个班级
- **班级进度**：这是这次设计上比较讲究的一个查询——用 `LEFT JOIN LATERAL` 让"这个学生根本还没做这份作业"显性地显示出来（`best_score` 是 `NULL`，`attempts` 是 `0`），而不是查询结果里直接不出现这一行。对老师来说"谁还没交作业"跟"谁交了多少分"是同等重要的信息，这个设计是特意保留"没做"这个状态的。

### 实测过的完整链路

用 curl 走了一遍：业者建老师账号 → 老师登入建班级 → 把之前家庭流程里建过的学生（陈小明）加进班级（用IC查找，加入前特意测过"IC格式不对"和"这个学生不存在"两种输入的报错分开测过）→ 建立作业分配 → **先查一次班级进度（学生还没做过），确认显示"未做"状态**（`best_score: null`, `attempts: 0`）→ 让那个学生实际提交一次成绩 → **再查一次班级进度，确认正确显示分数**（4/5）→ **权限边界测试**：业者账号（不是这个班的老师）尝试查看班级进度，正确被拒绝（"Not your class"）→ 学生账号尝试建班级，正确被拒绝（没有 `classes.manage` 权限）。

### 新增前端：`pages/edu/TeacherClassesPage.tsx`

班级列表 → 点进去展开三块：学生名单（加学生用IC）、作业列表（分配作业时是"先选课程、再选课程底下的关卡"两层下拉，复用了课程设计模块已经有的 API，不用重新做一套课程选择器）、**全班进度表格**（横轴是作业、纵轴是学生，交叉格子显示分数或"未做"，一眼能看出全班哪些人卡在哪一关）。导航栏加了"我的班级"入口。

**验证方式**：跟其他前端页面一样，`tsc -b` + `vite build` 零错误，用 Vite dev server 单独请求过新页面确认编译链路没问题。

### 这条线目前没做的部分

- **按学生各自排课**（不同学生做不同关卡/不同进度）——现在是整班统一分配，架构文档设计的 `question_mode`/`pacing_mode`（比如"全班共用同一组随机种子的题目"）还没做
- **课堂节奏控制**（3.7 节设计的"锁定关卡，播放视频才能解锁游戏"那个实时同步机制）——这个需要 WebSocket，是完全独立的一块，没有牵动这次做的东西
- **老师批量建学生账号**——现在老师只能把"已存在"的学生拉进班级，没有"老师自己建学生账号"这条路径（这个权限逻辑上业者本来就该有，是否要开放给老师是个产品决策，这次没做）

### 三条角色旅程都跑通之后，现在整个系统能做的事

- **业者**：建课程、建关卡、建老师/学生账号、管理等级体系
- **课程设计者**：建课程、加关卡（六种游戏模块+可操作互动的应用题）
- **家长**：注册、试用、订阅、加孩子、看孩子的学习记录
- **老师**：建班级、拉学生进班、分配作业、看全班进度
- **学生**：登入（IC）、玩关卡（订阅有效期内）、成绩自动记录

这五个角色的旅程现在都有真实可用的后端 API + 前端页面，不是只有学生端能玩、其他都是纸上设计。

## Phase 1+1 续：家长可以帮孩子重设密码了

`auth.controller.ts#forgotPassword` 一直是个空壳（没有真的发邮件），孩子密码忘了之前只能重新加一次账号或者手动改数据库。这次直接补上一个实际能用的版本——不用等接真的"忘记密码"邮件流程，家长本来就是孩子账号的监护人，直接给他一个"重设密码"按钮更实际。

**后端** `family.controller.ts#resetChildPassword`：跟其他碰孩子资料的端点（`subscribeChild`/`getChildProgress`）用同一套 `guardian_relationships` 权限检查，不是这个孩子的监护人不能重设。密码可以家长自己填，也可以留空自动生成（生成的密码只在这次回应里显示一次，跟建账号时同一个套路）。重设成功后**顺手把这个孩子所有装置的登入状态都撤销**，跟自助改密码（`changePassword`）是同一个安全逻辑——密码换了，旧的登入状态不该继续有效。

**实测过**：重设（自动生成密码）→ 用旧密码登入确认被拒绝 → 用新密码登入确认成功 → 权限边界测试（不相关的业者账号想重设，正确被拒绝）→ 用自定义密码重设一次，确认也能正常登入。

**前端**：`FamilyDashboardPage.tsx` 每个孩子旁边加了"重设密码"按钮，弹窗里可以选填新密码，成功后如果是自动生成的会显示一次性的密码文字（提醒"请记下，只显示这一次"），文案也提醒了家长"孩子原本登入的装置会被登出"。

## Phase 1+1 续：订阅绑定到等级（不是无限制访问全部课程）

之前订阅只有"有没有效"这个维度，没有限定"能玩什么"——这次加上：**订阅绑定到一个等级（L1-L4），订阅哪个等级，那个等级下所有课程都能玩，其他等级不行**。这个不是摆设，是真的在后端做了权限拦截，不是只在前端隐藏。

### 数据表

`db-migrations/010_subscription_grade_tier.sql`：`edu.subscriptions` 加了 `grade_tier_id` 外键。旧的（这次改动之前建的）订阅记录这个栏位是空的，会被当成"没有等级权限"处理——这批测试数据本来就是随时可以重建的，不是正式环境，没有做旧资料回填。

### 后端改动

**`family.controller.ts#addChild`**：现在**强制要求** `grade_tier_id`，不给就直接拒绝，并给出清楚的提示（"pick which level to start the trial in"）。传进来的等级会先验证是不是真的存在，不是随便一个字符串就收。

**`courses.controller.ts#getLevel`**——这是真正的权限关卡，加了一段：如果是 STUDENT 角色，查这个学生当前的订阅是哪个等级，再查这一关所属的课程是哪个等级，两者对不上就拒绝，回"这门课不在你订阅的等级里"。**这个检查只对 STUDENT 角色生效**，课程设计者预览自己做的内容、老师检查分配的作业，都不受影响——这是刻意的，这个限制是"付费墙"，不是"内容保护"，不该挡到内部角色做自己的工作。

**实测过**：
1. 加孩子不给等级 → 正确被拒绝
2. 加孩子给 L1 → 订阅正确记录 `grade_tier_id`
3. 建了一门 L2 专属的课程 → L1 订阅的孩子尝试玩 L2 的关卡 → **正确被拒绝**（"这门课不在你订阅的等级里"）
4. 同一个孩子玩 L1 的关卡 → 正常
5. 业者账号（非学生角色）访问 L2 的关卡 → 不受影响，正常能看（确认权限检查真的只挡学生）

### 前端

「添加孩子」弹窗加了等级下拉框（必选，不选不给交），旁边加了一句说明"订阅是按等级算的，这个等级下所有课程孩子都能玩"；「我的孩子」列表现在会显示每个孩子订阅的等级徽章（比如 `L1`）跟原本的订阅状态徽章并排显示。

## 迷宫模块：真正的"课程设计者制作内容并保存"——不是随机生成

这个是直接回应"系统应该能让课程设计者制作画面、题目并保存，不是什么都随机生成"这个问题做的。迷宫本来就是两个还没接进真实系统的模块之一，刚好借这个机会，从一开始就按"内容是设计出来、存下来的"这个原则做，不是"给几个参数、程序生成"。

### 为什么迷宫天生就该是"authored"而不是"generated"

迷宫这个模块，随机生成参数（比如"网格大小"、"墙壁密度"）根本生成不出"好玩、有意义"的迷宫——这跟点点数数（给个范围随机出几个数字就是一道合理的题）本质不同。所以 `edu.maze_configs` 表里存的不是"生成这个迷宫需要的参数"，而是**这个迷宫本身**：背景图片URL、画好的路径遮罩图URL、起点终点坐标——每一个栏位都是"这就是内容"，不是"用来生成内容的设定"。

### 数据表

`db-migrations/011_maze_module_authored_content.sql`：`edu.maze_configs`——`bg_image_url`（背景美术图）+ `mask_image_url`（课程设计者画出来的路径遮罩，非透明的像素就是能走的路）+ 起点终点坐标。后端建立关卡时会**强制要求**这两张图都要有，不给直接拒绝创建（实测过，拿掉图片故意测试，正确被拒绝，提示"bg_image_url and mask_image_url are required for maze"）——这跟点点数数那种"什么都不填也有合理默认值"的行为刻意不同，因为迷宫没有"合理默认值"这回事，没有实际内容就不该能建关卡。

### 课程设计者的画路径工具

`CourseDesignerPage.tsx` 里加关卡弹窗新增"迷宫"选项：
1. 上传背景图片
2. **画路径**——按住拖动直接在图上涂出孩子能走的路（用的是 canvas 实时绘制，不是点几个点连线那种简化版）
3. **擦除**——涂错了可以擦掉重画（用 canvas 的 `destination-out` 合成模式实现真正的擦除，不是盖一层白色遮住）
4. **设起点/设终点**——切换到对应模式后点一下图上的位置
5. 保存时把画好的路径遮罩导出成 PNG（`canvas.toDataURL`），连同背景图、起点终点一起存进 `maze_configs`

### 学生端玩法

`games/MazeGame.tsx`——不是"看图片选答案"，是真的用 canvas 像素采样做碰撞检测：玩家拖着小球移动，每次移动都去遮罩图对应位置采样一次透明度（`getImageData`），透明度够高才算"走得通"，否则原地不动、提示"这里走不通"。这是真正的迷宫玩法，不是"点哪里都能到终点"的假迷宫。

**实测过**：建课程 → 加一关迷宫（背景图+遮罩图+起点终点）→ 拉取关卡确认配置完整组装（图片URL、坐标都对）→ 故意不给图片测试建关卡，确认被正确拒绝 → 确认课程列表没有回归问题（13→14）。

### 这个模式怎么推广到其他模块——不是只有迷宫该这样

这次除了做迷宫，也把这个原则想清楚了，写下来方便之后照着做：

| 模块 | 现在的状态 | 要补的"authored"能力 |
|---|---|---|
| **找不同** | ✅ 已经是对的——上传两张图+标记差异点，存的是真实内容 | 不用改 |
| **迷宫** | ✅ 这次做的 | 不用改 |
| **点点数数** | 只有随机生成（主题+范围+题数） | 可以加一个"自定义画面"模式——课程设计者上传一张场景图 + 在图上标记"这里有几个物件"的具体位置和数量，存成固定题目，跟现有的"随机生成"模式并存（关卡建立时选"随机"还是"自定义"）
| **专注力点数字** | 只有网格模式 | 数据库栏位其实已经预留了"自定义图片模式"（`bg_image_url`/`positions`），当初设计时就说了"引擎和设计器UI还没做"，现在可以照迷宫这次的模式补上——上传图片，标记数字要出现的具体位置
| **Memory配对** | 只有主题图库（emoji） | 加"自定义图片"选项——课程设计者上传好几组图片当作配对素材，取代/补充emoji主题
| **找规律** | 只有算法生成的规律（AB/ABC等） | 这个比较难改成"authored"，规律本身适合用算法生成，可以考虑的是让课程设计者上传"图案素材"取代emoji，但规律序列本身继续用算法生成
| **应用题** | 只有公式生成（鸡兔同笼/相遇问题） | 可以加"手动出题"模式——课程设计者直接打字写题目+设定答案，存成固定题目，跟公式生成的题目混在一个题库里随机抽

**这不是说"随机生成"就该被取代**——两种模式其实互补：随机生成适合"练习量大、答案是算出来的"这类题目（点点数数、应用题），authored 内容适合"有具体场景、需要设计感"这类题目（迷宫、找不同）。系统该做的是让课程设计者两种都能选，不是二选一定死。这次先把"authored"这条路径证明是可行的（迷宫），之后要往其他模块补的时候，照这个表一个一个加，不是重新设计。

## 专注力点数字补上"自定义场景"模式——路线图的第二项

按上次列的表，这次做的是专注力点数字的自定义图片模式——数据库栏位（`bg_image_url`/`positions`）当初建 focus_tap 模块时就预留了，玩法引擎（`FocusTapGame.tsx`）跟部分设计器代码之前也已经写了大半，但少了最关键的一块：`FocusTapCustomDesigner`——课程设计者实际标记位置用的那个组件——**只有调用没有定义**，会直接编译失败。这次补上这个组件，才算真正完整能用。

### 玩法

课程设计者上传一张场景图（比如一只卡通动物），点图上想让数字出现的位置（比如头顶、两只手、脚下），点几个位置就有几个数字。跟找不同的标记交互是同一套——点空白处新增标记、点已有的标记移除，不是重新发明一套操作方式。存下来的是**这些位置本身**，不是"生成N个位置"的参数——**位置是设计出来的，但每次玩哪个数字对应哪个位置，还是会重新随机分配**（这个随机化正是专注力练习真正要练的东西，跟位置本身该不该随机是两回事）。

### 后端验证

`courses.controller.ts` 建关卡时已经有验证：`custom` 模式必须要有背景图，且至少标记2个位置才给建——实测过，只标记1个位置去建关卡，正确被拒绝，报错信息清楚（"custom 模式的专注力点数字需要背景图和至少2个标记位置"）。

**实测过**：标记不足2个位置 → 正确拒绝；标记3个位置正常建立 → 拉取关卡确认配置完整组装（背景图+3个坐标都对）→ 确认原本的格子模式没有回归问题 → 课程总数正确增加。

路线图上还剩：点点数数的自定义场景模式、Memory的自定义图片配对、应用题的手动出题模式——照这次同样的路数，一个一个补。

## 素材库上线——图片可以重复用了，不再是每次都用完即丢

之前不管是找不同、迷宫、还是专注力的自定义模式，上传的图片都是一次性的——直接嵌进那一关的 config，用一次就绑死在那，下次要用同一张图还得重新选一次文件。这次建了真正的素材库，上传一次，之后任何关卡都能从库里挑，不用重新上传。

### 数据表

`db-migrations/012_asset_library.sql`：`edu.assets`——分类（背景图/物件图案/图标/其他）、名称、图片数据、上传者。**存储方式还是 base64 存在 TEXT 栏位**，跟这个项目至今所有图片的存法一致，没有另外接文件存储服务——这个决定是刻意的：素材库真正的价值在于"能重复选用"，不在于换一种存储格式，先把复用这件事做对，以后真要换成对象存储（S3之类），这张表的形状几乎不用改，只是 `file_data` 从"就是图片本身"变成"图片的URL"。

### 后端

`assets.controller.ts`：上传、列表（支持分类筛选+名称搜索+分页）、取单个、删除。**列表接口刻意不回传 `file_data`**——缩略图网格一次要显示几十张，每张都带完整 base64 数据没有必要，列表只回传 id/分类/名称/尺寸这些轻量栏位，点开某一个才去拉完整图片数据。删除权限是"只有上传者本人能删"，实测过教师账号想删除业者上传的素材被权限挡下（虽然实际挡下的是 `courses.manage` 这一层，教师本来就没这个权限，两层防护都在）。

**实测过**：上传3个不同分类的素材 → 列表正确显示、按分类筛选正确 → 确认列表真的不含 `file_data`、单独取一个素材才有完整数据 → 删除权限边界测试（非上传者被拒绝）→ 上传者删除自己的素材成功。

### 前端

**`AssetLibraryPage.tsx`**——独立的素材库管理页面，网格浏览、按分类筛选、搜索、上传、删除（hover 显示删除按钮），导航栏加了"素材库"入口。

**`components/AssetPicker.tsx`**——这是给其他模块设计器用的可复用组件，不是只服务这一个页面。一个按钮，点开弹窗有两个分页："从素材库选"（网格选择已有素材）和"上传新图片"（上传的同时自动存进素材库，不用先去素材库页面传好再回来选）。**这次先接进迷宫的背景图片上传**作为验证——原本迷宫加关卡那里只有一个裸的文件选择框，现在旁边多了"从素材库选"这个按钮，两种方式并存。

**下一步**：这个 `AssetPicker` 组件是设计成即插即用的，接下来要把找不同的两张图片上传、专注力自定义模式的背景图片上传也换成同一个组件，不用重新设计——这也是"素材库是地基"这句话的意思，其他模块换过来是小改动，不是重新做。

## AssetPicker 接进找不同和专注力自定义模式

上次说的"接下来要把找不同的两张图片上传、专注力自定义模式的背景图片上传也换成同一个组件，不用重新设计"——这次做了，而且确实是小改动：

**找不同**：原本的 `handleUpload(side, file)` 拆成两层——`handleUpload` 负责从文件读出 dataURL，`handleSelect(side, dataUrl)` 负责真正处理图片（加载进 canvas、更新状态），`AssetPicker` 直接调用 `handleSelect`，跳过"读文件"这一步（因为素材库来的图片已经是 dataURL 了）。原图、找不同图两个位置各自加了"🗂️ 从素材库选"按钮，跟原本的文件选择框并排。

**专注力自定义模式**：同样的拆分方式，`FocusTapCustomDesigner` 组件里加了 `handleSelect`，背景图片旁边加了"🗂️ 从素材库选"按钮。

## 学习时长统计上线——顺带抓到一个严重的既有 bug

按"每个学生做题、登入、退出的时间需要记录"这个需求做的。好消息是数据其实一直都在记：登入建 session 记录、登出（主动或被单一会话踢下线）记录结束时间、token 刷新会更新最后活跃时间。缺的是把这些原始记录整理成"这个学生这次到底学了多久"这种能看的统计。

### 一个必须先解决的技术坑：refresh token 轮替把"一次登入"切碎了

现在的刷新令牌机制每次刷新都会撤销旧的 session 记录、建一条新的（这是正确的安全做法——每个刷新令牌只能用一次）。但这意味着学生体感上"一次连续登入"，在数据库里其实是一串短记录串起来的，大概每15分钟（access token 的有效期）就断一次。如果直接拿单条记录算时长，量出来的是"两次刷新之间"这么短的片段，会严重低估真实学习时间。

`db-migrations/016_session_chain_tracking.sql` 加了 `session_chain_id`——同一次连续登入（原始登入+后续所有刷新）共用一个 chain id，统计的时候按 chain 分组，用 `MIN(建立时间)` 到 `MAX(最后活跃时间)` 算出真实的登入时长，不是按单条记录算。

### 测试这个功能的时候，顺带抓到一个更严重的问题

测试"登入→刷新→刷新→登出"这条链路时，**刷新直接失败了**——查下去发现 `refreshToken()` 里有一段用 `jwt.verify()` 去验证刷新令牌的代码，但刷新令牌本身根本不是 JWT（就是32字节的随机字符串），这段验证**永远会失败**，让每一次刷新请求都被拒绝。这其实是这个项目最早期（Phase 0）就出现过、我以为已经修好的同一个bug——不知道什么原因又出现在代码里了。这次直接把这段没用的验证拿掉，真正的验证靠后面的数据库查询（比对哈希值+确认没被撤销+没过期）完成，这本来就是原本设计要用的验证方式。

**这个 bug 不只是"这次新功能测不了"这么简单**——它意味着任何时候学生的 access token 过期后尝试自动刷新，都会失败（逼学生重新登入），而且会让所有的学习时长统计看起来都异常短（因为每次"刷新失败"都被误判为"这个学生放弃了、没有真的用多久"）。找到并修掉这个是这次最重要的产出，比学习时长统计功能本身还重要。

### 实测过的完整链路

登入 → 刷新 → 刷新 → 主动登出，全部成功（之前刷新那两步全部失败）→ 家长端查询学习时长，确认这整条链路被正确合并成**一次**约3秒的登入记录，不是被切成3段各自独立的短记录 → 教师端查班级学习时长汇总，正确显示。权限边界测试（业者账号想看不相关学生的学习时长，正确被拒绝）。

- 家长的"学习记录"弹窗最上面加了"最近14天学习时长"汇总 + 每日明细
- 老师的班级学生名单，每个学生名字旁边显示"14天学X小时X分钟"

## 图片上传失败——找到真正原因并修了

这次报告的"图片上传失败"，实测复现：Express 的请求体大小限制是10MB，但**base64编码会让文件体积膨胀约33%**，一张稍微大一点的照片（尤其是手机直接拍的，很容易5-15MB）编码成base64就轻松超过10MB。超过限制时，原本的全局错误处理器把所有错误都笼统地回"Internal server error"，用户完全看不出问题出在哪，感觉就是"莫名其妙上传失败"。

**修了两处**：请求体大小上限从10MB提到20MB（给真实照片更多余量），并且给"文件太大"这种情况加了专门的判断，回传清楚的提示（"文件太大了，请换一张小一点的图片或视频，上限20MB"）而不是笼统的"Internal server error"。前端这边也把 `AssetPicker`/`AssetLibraryPage`/`ImageEditorPage` 里原本吞掉后端具体错误信息、只显示"上传失败"的地方，改成把后端的具体原因显示出来。

**实测过**：故意传一张~21MB的图片，确认现在会收到清楚的413错误和提示文字，不再是一头雾水的500错误。

`db-migrations/017_asset_classification.sql`：素材库的每个素材现在可以标记"适用哪个游戏模块"（迷宫/找不同/专注力/...）、"适用哪个等级"、"语言"（通用/中文专用/英文专用——纯图案没有文字的选通用，图里嵌了中文字的标中文专用）。全部选填，不影响任何已有素材。

### 统一到每个游戏模块——不用一个个模块单独接

这是这次最关键的架构决定：把编辑器的核心逻辑抽成一个独立组件 `SceneEditor.tsx`，`ImageEditorPage`（独立页面）只是套了一层页面外壳来用它；`AssetPicker`（找不同、迷宫、专注力自定义模式现在都在用的选图组件）多了第三个分页"🎨 编辑/制作"，点开就是完整的 `SceneEditor`。这样**任何已经在用 AssetPicker 的地方，自动就有完整的编辑能力**，不需要一个个模块单独去接编辑器——这就是"所有游戏模块都用同一个编辑器"这句话真正的意思：不是复制粘贴同一套代码到七个模块里，是七个模块共用同一个组件实例。

**实测过**：`tsc -b` + `vite build` 零错误（包括 AssetPicker 和 SceneEditor 之间的循环引用——两者互相用到对方，正常来说要小心，但因为都只在渲染时才用到对方、不是在模块顶层执行时依赖，所以是安全的循环引用，编译和打包都验证过没问题）。素材分类的后端接口测过创建、按模块筛选、默认值（不填的话 language 默认是"通用"）都正确。

## 迷宫画路径工具补齐：桶装填色 + 可调笔刷宽度

最早的迷宫原型设计里本来就有笔刷、桶装填色（bucket fill）、屏障线三个工具，接入真实系统时为了控制范围只留了笔刷（+擦除），桶装填色被砍掉了，笔刷宽度也是写死22px、没有做成可调。这次把这两个补上（屏障线工具这次还是没做，范围还是刻意收着）。

### 笔刷宽度可调，能画得很细

工具栏笔刷/擦除模式下方多了一个宽度滑杆（2~50px），不再是写死的22px——需要画细一点的路径（比如比较窄的通道）现在做得到。

### 桶装填色

新增"🪣 填充"工具——**跟画笔/擦除不一样，这个是点一下生效，不是按住拖动**（拖动会在每个移动点上重复触发整个画布的填色运算，既没必要也浪费性能，所以特意做成单击触发）。用法：先用笔刷画出一个封闭区域的边界，再用填充工具点一下里面，整个封闭区域瞬间填满，不用一笔一笔涂。

**算法实现**：用像素的透明度分类"空白"跟"已经画过"两种状态，从点击的位置开始做连通区域填充（用不递归的堆栈方式，900×620这么大的画布如果用递归实现，填充大范围区域可能撑爆调用栈，所以特意写成用数组模拟堆栈的迭代版本）。

**验证方式**：写了一个 Node 测试，模拟一个20×20的网格，画一个10×10的空心方框当作"墙"，从方框中间点击填充，确认精确填满了方框内部的64个格子（10×10减去边框），而且验证了方框外面的格子完全没被动到——填色不会"漏"到封闭区域外面，这是这个工具能不能用的关键，不是"看起来差不多"就算过。

## 两个坏掉的问题都修了

### 迷宫填充"点一下整张图被覆盖"

不是算法写错——空画布上点"填充"，从没有边界的地方开始蔓延，本来就会填满整张图（这是任何画图软件桶装填色的标准行为，不是bug）。真正的问题是**完全没有安全网**——不小心点一下就把之前画的路径全部盖掉，没有撤销可以救。

**修了两处**：
1. **撤销功能**——每次画笔/擦除/填充操作之前都会存一份快照（最近20步），点"↩️ 撤销"能退回上一步
2. **"🗑️ 删除颜色"工具**——填充的反向操作，点一下能把连在一起的一整块颜色清掉，专门用来应对"不小心填满了怎么办"这种情况

**验证方式**：写了 Node 测试模拟"整张画布不小心被填满"这个最坏情况，确认"删除颜色"工具点一下能把整张图完全清空恢复，这条链路是通的。

### 登入后所有身份都看到一样的选项

这个是真的漏了——`roleCodes` 这个变量在代码里其实一直都算出来了，但从来没有拿去做任何过滤，导致不管是学生、家长、老师、业者，登入之后侧边栏看到的选项完全一样。

**修了**：每个导航连结现在会检查目前登入者的身份是否真的需要用到那个功能——学生看得到"课程/关卡"，家长看得到"我的孩子"，老师看得到"我的班级"，业者/课程设计者看得到"课程设计""素材库""图片编辑工具""等级管理"，业者才看得到"机构/分校"。一个人如果身兼多个身份（比如业者同时也是老师），看到的是所有相关身份选项的并集，不是只能选一个。

顺带把首页也重做了——之前首页其实是 Phase 0 留下的占位页面，明明写着"接下来会依角色显示不同内容"，但从来没真的做（这个占位页面本身也是"权限没有生效"这个问题的一部分）。现在首页会显示跟当前身份相关的快捷入口卡片，不是一段静态文字。

**验证方式**：确认 `/auth/me` 后端接口本来就正确回传角色数据（这块后端没问题，纯粹是前端拿到数据后没有拿来用），`tsc -b` + `vite build` 零错误，后端课程数量确认没有回归。

## 习题编号系统上线——"关卡"全面改称"习题"

### 命名决定

前端所有中文显示文字里的"关卡"都换成了"习题"（`grep` 一次性替换，检查过没有误伤实际的变量/函数名，那些照旧是英文的 `level`/`Level`）。**数据库表名 `course_levels` 没有跟着改**——这是刻意的决定：表名只是内部实现细节，用户根本看不到，改表名要牵动几十个查询和类型定义，风险跟工作量都不成比例，真正要改的是用户"看到"的文字，这个已经做到了。

### 三层分类 + 自动编号

`db-migrations/018_exercise_classification.sql`：
- `exercise_categories`（习题大种类）——七个游戏模块各自对应一个分类（迷宫/找不同/专注力/Memory/点点数数/找规律/应用题），每个分类带一个可自定义的编号前缀（迷宫=MK，找不同=FC...），这个前缀存在数据库里，不是写死在代码里，符合"PREFIX 可以根据数据库表里的预设值自定义"这个要求
- `exercise_groups`（分类）——大种类底下的子分类，比如迷宫底下的"数字迷宫""动物迷宫"，**不是固定枚举，课程设计者可以随时新建**

**编号生成**：`exercise_number_counters` 表按"大种类+分类"这个组合各自维护一个独立的计数器，用 `INSERT ... ON CONFLICT DO UPDATE` 做原子递增，两个课程设计者同时在同一个分类底下建习题也不会撞号。

**实测过完整流程**：建"数字迷宫""动物迷宫"两个分类 → 在"数字迷宫"底下连建两个迷宫习题，确认编号是 `MK-NUM-10001`、`MK-NUM-10002`（连续递增）→ 在"动物迷宫"底下建一个，确认编号是 `MK-ANIMAL-10001`（**独立计数器，从头开始，不会接着上一个分类的号码走**）——这两个结果完全对上你原本举的例子（mk10001/mk20001，两个分类各自从10001起跳）→ 建一个完全不分类的习题，确认能正常保存、编号是空的，不会因为没分类就报错。

课程设计弹窗里加了"习题分类"区块——选大种类（下拉，选了游戏模块类型会自动带出对应的大种类，省一步）、选分类（会跟着大种类联动过滤）、"+新分类"可以当场新建一个分类不用等别人去后台加、小分类下拉。全部选填，不选也能正常保存，编号栏位就是空的，之后随时可以回来补。习题列表现在会在标题旁边显示编号（有编号才显示）。

### 学生小组：排课对象从"班级"扩展成"个人/班级/小组"三选一

## 画布统一尺寸 + 迷宫走过路径标记 + 卡片阴影视觉升级

这次做的三件事都是系统性的（改动分布在很多文件），先说清楚做了什么、没做什么。

### 统一画布尺寸

新建了 `frontend/src/lib/gameCanvas.ts`，导出唯一的 `GAME_CANVAS_W = 1100, GAME_CANVAS_H = 700`——这是目前几个画布尺寸里最大的那个（原本迷宫900×620、找不同1100×620、专注力自定义900×560、点点数数自定义没有固定尺寸），统一成这一个，而且是几个原尺寸里最大的，符合"尽量大"这个要求。

**改动的地方**：`MazeGame.tsx`、`SpotDiffGame.tsx`、`SceneEditor.tsx`（图片编辑工具+AssetPicker里的编辑分页共用这个）、`CourseDesignerPage.tsx` 里迷宫/找不同/专注力自定义模式的设计器画布——全部改成引用同一个常数，不是各自写死一个数字。找不同的左右两个图片框跟着新的画布高度重新计算了一次（原本580px高改成655px，尽量把新增的高度空间用起来，不是留白）。

**关于"物件图片跟着比例放大"**：点点数数自定义模式跟专注力自定义模式的物件/数字标记，原本是写死的像素大小（比如 `w-12 h-12`），现在改成画布宽度的百分比（`w-[7%]`）——画布不管渲染多大，标记跟画布的比例关系都一样，不会出现"画布变大了但图钉还是那么小"的问题。这两个游戏的容器也改成用 `aspect-[11/7]` 固定比例（对应1100:700），不再是任意的 `min-h` 或写死的宽高比数字。

### 迷宫：走过的路要标记，能清除/擦除

`MazeGame.tsx` 新增：球每次移动到新位置，就在那个位置留一个半透明的小圆点（橙色，跟球的颜色呼应），一路留下痕迹，学生能看到自己已经走过哪里。

工具栏加了三个按钮——"🖊️ 走路"（默认，拖球走迷宫）、"🧹 擦掉走过的路"（切到这个模式，在画布上拖动能擦掉附近的痕迹点，不影响球的位置或迷宫本身能不能走）、"🗑️ 全部清除"（一键清空全部痕迹）。**这个只是视觉记录，不影响游戏逻辑**——擦掉痕迹不代表"没走过"，球已经验证过的位置、迷宫本身的可走性判定完全不受影响，纯粹是给学生自己看的路线记录。

**验证方式**：写了 Node 测试模拟50个痕迹点排成一条线，在某个点附近"擦除"，确认只清掉了那附近的3个点，其他47个完全没被动到——这个局部擦除不会不小心把整条痕迹都清空。

### 卡片+阴影视觉升级

迷宫、找不同、专注力点数字（格子模式+自定义模式）、点点数数（两种模式）、Memory配对、图片编辑工具——这些游戏/工具的主画布容器统一加了 `shadow-lg ring-1 ring-black/5`（明显的阴影+极淡的描边），让画布从背景里"浮"出来，比原本纯色块的观感更精致。找规律、应用题这两个模块因为本来就是文字/卡片式布局、没有一个"画布"的概念，这次没有套用（套用了反而不搭）。

### 这次没做的（下一步清单）

- **找规律、应用题的自定义背景图/物件图上传**——你信息里提到跟 Memory、点点数数一样处理，这次先做了系统性的画布统一和迷宫功能，这两个模块的自定义模式留到下一轮
- **画布尺寸变动对已经存在的自定义场景（比如上次测试建的那几个）**——这些关卡存的是**归一化坐标**（0~1之间的比例，不是写死的像素位置），所以换了新的画布尺寸完全不受影响，坐标自动对应到新尺寸上的正确位置，不用重新标记

## 加习题弹窗尺寸统一——之前确实是按模块类型分开判断的，这次改成统一

你截图指出的问题是真的：`size={moduleType === "spot_diff" || moduleType === "maze" || (moduleType === "focus_tap" && ftMode === "custom") ? "full" : "md"}"` 这行代码，只有找不同、迷宫、专注力自定义模式才给"full"尺寸，**上一轮新加的点点数数自定义画面模式漏掉了**——所以点点数数选"自定义画面"时，理论上该显示1100×700的标记画布，却被塞进一个"md"（384px）的窄弹窗里，会挤成一团。Memory、找规律、应用题这几个则是从来没在这个判断式里出现过，一直都是窄的。

**修法**：直接把这个按模块类型判断的逻辑拿掉，`size="full"` 现在是所有模块统一用的固定值，不再有"某些模块窄、某些模块宽"这种不一致。

### 顺便发现"full"本身也不够大

原本 `full` 尺寸对应 `max-w-4xl`（896px）——但游戏画布内部分辨率是1100px（上次统一的那个尺寸），塞进896px的弹窗里还是会被压缩。这次把 `full` 改成 `max-w-6xl`（1152px），刚好能完整容纳1100px画布+左右内边距，不会再被二次压缩。**而且这个尺寸跟做题界面（`LevelPlayerPage.tsx`）本来就在用的 `max-w-6xl` 完全一致**——这就是你说的"务必要和做题的界面一样大"，现在设计弹窗跟实际玩的界面用的是同一个宽度基准，不是碰巧看起来差不多。

### 响应式处理

顺带发现一个更早就存在的小问题——弹窗容器原本用 `w-full`，在固定定位（`fixed`）下这个会撑满整个视窗宽度，在很窄的手机屏幕上会直接顶到屏幕左右两边，没有任何呼吸空间。这次改成 `w-[calc(100%-2rem)]`——不管屏幕多窄，两侧至少留1rem（16px）的安全边距，同时大屏幕上仍然会被 `max-w-6xl` 这个上限卡住，不会无限变宽。

**验证方式**：`tsc -b` + `vite build` 零错误，Vite dev server 确认 `modal.tsx` 和 `CourseDesignerPage.tsx` 编译链路正常，后端课程数量确认没有回归（这次是纯前端改动，没有碰任何后端/数据库代码）。

## 修了保存习题时的 500 报错——"选了大种类、没选分类"这种情况

你截图报的这个错，复现了：`edu.exercise_number_counters` 这张表的主键是 `(category_id, group_id)` 两个栏位组成的——Postgres 的复合主键会**自动**要求组成它的每一个栏位都不能是 NULL。这本来在"大种类+分类都选了"的情况下没问题，但**"只选大种类、不选分类"这个用法从一开始就是设计上明确支持的**（弹窗文案本来就写着"不选也可以正常保存，之后再补分类"），这种情况下 `group_id` 就是 NULL，直接撞上主键的非空限制，后端报错、前端显示"新增失败"。

### 修的过程中踩了一个坑，一并记录

第一次修的时候，把复合主键换成独立的 `id` 主键，理论上这样 `group_id` 就不用再被强制非空了——但**跑完这个 migration 之后，用截图里同样的操作重新测了一次，还是同一个错**。查下去才发现：Postgres 里"复合主键让每个栏位变NOT NULL"这件事，是**独立设置在栏位本身上的一个约束**，不是绑定在主键约束上的——拿掉主键，并不会自动把这个 NOT NULL 也拿掉。要另外单独执行 `ALTER COLUMN group_id DROP NOT NULL` 才行。这一步一开始漏了，这次已经补进 `021_fix_exercise_counter_null_group.sql` 这个migration文件里，不是只在这次的资料库里手动补了一次而已。

### 验证方式

**完整复现过整个问题**：用跟截图完全一样的操作（选了"专注力点数字"这个大种类、分类留空）去建习题，第一次改完还是报同样的错 → 找到 NOT NULL 那个坑、补上 `DROP NOT NULL` → 重新测，这次正确建立成功，习题号码是 `FT-10001`（只有大种类前缀，没有分类代号，因为分类没选）→ 再建一个同样只选大种类的，确认编号正确递增到 `FT-10002` → **回归测试**：确认原本"大种类+分类都选"这条路径没有被这次改动破坏，编号正确接着之前测过的序列往下走（`MK-NUM-10003`）→ 确认这个修复的 migration 文件本身是幂等的（重复跑一次不会报错，只会跳过已经存在的部分）。

## 一次很长的 migration 排查——记录下来，避免以后重蹈覆辙

这次花了不少来回才解决的问题，值得写清楚，方便之后遇到类似情况能更快定位。

### 表面现象 vs 真正原因

一开始看到的是"加习题弹窗窄小不统一"，修好之后又冒出"保存时500报错"，一路排查下来，牵出了**三个独立但表现类似的问题**：

1. **`021`**：`exercise_number_counters` 的复合主键会自动把 `group_id` 变成 NOT NULL，"只选大种类不选分类"这个明确支持的用法会直接违反这个限制——这个是设计上的漏洞，已经在代码层面修好并写进 migration。

2. **`020` 没跑完整**：`counting_configs` 缺了 `positions` 栏位（`mode` 有加进去，`positions` 没有）。

3. **`018` 没跑完整**：`course_levels` 缺了 `group_id`、`curriculum_type_id`、`exercise_number` 三个栏位（`category_id` 有加进去，其他三个没有）。

### 后面两个问题的根本原因：SQL 执行方式

排查过程中发现一个模式——**同一个 migration 文件里，前面几句执行了，后面几句没执行**。这种"部分执行"的情况，最常见的原因是 DBeaver 里用 `Ctrl+Enter`（只执行光标所在那一句）代替了 `Alt+X`（执行整个脚本）。这不是这次代码或 migration 文件本身写错了，而是**执行方式**的问题——以后每次跑 migration 文件，务必确认是用"执行整个脚本"这个操作，不是一句一句手动跑。

### 诊断这次问题时用的方法，也记录一下

DBeaver 里显示改对了，但应用程序还是报同样的错——这种"看起来改了但实际没生效"的情况，最快的排查方式**不是继续在 DBeaver 里确认**，而是让后端自己在启动时打印一次它实际看到的表结构（临时在 `app.ts` 里加一段查询+`console.log`）。这样能排除"DBeaver 连的是另一个数据库/另一个 schema"这类可能性——因为这次诊断用的就是后端处理所有真实请求的那一条数据库连线，看到的结果保证就是后端实际的状态，不会有连错地方的疑虑。

## 编号前缀管理界面

之前"习题大种类"（`exercise_categories`）和"分类"（`exercise_groups`）的前缀，只能透过"加习题"弹窗里"新分类"这个入口临时新建，**没有任何地方能看已经有哪些、改前缀、或删掉不要的**——这次补上一个专门的管理页面，`/exercise-prefixes`，导航栏"编号前缀管理"。

### 设计成可替换的储存模块

新建了 `backend/src/utils/assetStorage.ts`，这是**唯一**决定图片实际存在哪里的地方——现在实现是写到本机磁盘（`backend/uploads/assets/`），透过后端本来就有的静态文件服务对外提供。以后要换成真正的远端储存（S3之类的），只要换掉这一个文件里的实现，`assets.controller.ts` 和前端完全不用碰——它们从头到尾只处理"一个网址字符串"，不管这个网址背后是本机磁盘还是远端储存引擎。

**新增环境变量 `ASSET_BASE_URL`**——决定网址前面接哪个域名，本机开发默认是后端自己（`http://localhost:4000`），正式环境要改成真正对外的域名。以后换远端储存，也是改这一个变量指向那个储存服务的公开网址。

### 三种输入都处理了

- 上传新图片（base64）→ 写成文件，存网址
- 直接传一个已经是网址的字符串（比如以后要接外部图库，或课程设计者直接贴一个网络图片链接）→ **原样存下**，不会硬要重新处理成本机文件——这就是"网址可以是本机或远端储存"这句话字面上的意思
- **已经存在的旧素材（改之前上传的那些）完全不受影响**——它们的 `file_data` 还是原来的base64内容，没有被强迫迁移，因为对前端来说，不管是base64还是网址，反正就是塞进 `<img src="...">` 里，两者混着用完全没问题

### 旋转——之前整个编辑器都没有的能力

`SceneEditor.tsx`（迷宫、找不同、专注力、图片编辑工具都共用的那个编辑引擎）之前只能移动、缩放，这次加了**旋转**。选中物件或文字后，边框上方会浮出一个绿色把手，拖着它转圈就能转——不是拖蓝色的缩放把手（那个还是负责改宽高）。

## 修了"加物件后自动变大盖住背景图"这个bug

### 找到的原因

拖动缩放把手的时候，鼠标/手指移动的距离会被乘以**2倍**才换算成物件新的宽高——这个放大系数设得太激进了。刚加进画布的物件是120×120（相对1100px宽的画布，大概11%，本来是个合理的小尺寸），但只要有一次"想拖动物件去换位置，结果不小心抓到了右下角那个缩放把手"（这个把手离物件本身的编辑框很近，尤其触控的时候很容易手滑抓到），稍微拖个200px，物件就会因为2倍放大系数暴涨到520px（快要半个画布宽了）——这就是"自动变大盖住背景图"这个现象的真正原因，不是"自动"，是一次不小心的缩放操作被放大系数放大了后果。

**修法**：把这个2倍系数改成1:1——拖多少，物件就跟着变化多少，不会再有"稍微一碰就暴涨"这种情况。这个修改同时套用在背景图和物件两种缩放上。

**验证方式**：算了一下同样"不小心拖了200px"这个情况，改之前物件会长到画布宽度的47%，改之后只会长到29%——同样是一次不小心的操作，后果明显更可控、更符合预期。就算真的不小心碰到缩放把手，也不会一下子就跳到"整个盖住背景"这种夸张的程度，而且缩放过程是逐步跟着拖拽走的，能清楚看到自己在做什么，不会有"莫名其妙突然变大"的感觉。

- **顺带修了一个数独特有的正确性问题**：数独的正确答案本来就设计成不会传给学生（防止打开浏览器网络分页偷看答案）——但这个保护措施如果原封不动套在"设计者编辑自己出的题目"这个场景，会变成设计者自己都看不到自己写的答案，等于没办法编辑。新增了一个专门给设计者用的接口 `GET /levels/:levelId/edit`（需要课程管理权限，学生用不到），这个接口**才会**带上正确答案；学生实际玩习题用的接口维持原样，答案照样隐藏。两条路径分开，各自负责各自的场景。

- 顺带也把"验证失败的具体原因只有在开发模式下才看得到"这个问题一起修了——之前不管是建立还是现在新增的编辑，如果验证失败（比如忘记选背景图），在正式环境跑起来会被吞成笼统的"Internal server error"，看不出真正原因。现在validation类的错误统一会用清楚的400错误呈现，不分建立还是编辑。

### 前端

课程设计器的习题列表，每一行现在都有"编辑"和"删除"两个按钮。点编辑会打开原本"加习题"那个弹窗，但标题变成"编辑习题"、模块类型下拉框会锁住不能改、其他所有栏位（包括每个模块各自的具体内容——点点数数的物件位置、迷宫画好的路径、数独的每格答案等等）都会照原样带出来，改完存档走的是刚才说的编辑接口，不是重新建一个。删除会先跳确认对话框，删除失败（比如已经有学生玩过）会显示后端给的具体原因。

**验证方式**：建了一个习题，改标题/改设定/加提示文字，确认全部改动都正确存进数据库；删除一个没人玩过的习题成功；对一个已经有学生进度记录的习题尝试删除，确认被正确挡下来、提示清楚。数独这块额外测了一轮：学生用的接口确认看不到答案，设计者的编辑接口确认看得到，编辑一个数独（改答案+加一格）确认改动正确持久化，用编辑接口重新拉取验证过。

## 应用题新增两个分类：牛吃草、浓度问题

确认了分类没问题——相遇问题、牛吃草、浓度问题都属于应用题这个大类，这次把牛吃草和浓度问题也接上了随机出题引擎（跟原本的鸡兔同笼、相遇问题走同一套架构：题目文字模板+参数代入+互动式作答，不是选择题）。

### 数学生成方式：从答案往回推，不是生成完再检查

这两种题型如果用"先随机生成数字，再检查算出来的答案是不是整数"这种做法，很容易大部分随机结果都要丢掉重来（因为随机凑出来的数字，很少刚好能整除）。这次改成反过来——**先决定要用哪个整数当因数，再用这个因数反推其他所有数字**，这样保证从一开始生成出来的每个数字就已经是干净的整数，不需要事后检查、不需要重试。

**牛吃草**：经典的"牛顿牛吃草"问题——牧场的草每天固定速度生长，几头牛吃几天能吃完。设计上先决定草场生长速度和第一个场景的天数，反推出草场初始草量，然后从草量的因数里挑数字构造第二、第三个场景，保证怎么选都是整数。

**浓度问题**：稀释盐水的问题——原本浓度较高的盐水，加多少水能稀释到目标浓度。设计上让"原始盐水重量"直接等于"目标浓度 × 一个随机倍数"，这样"要加多少水"这个答案自动就是整数，不用额外检查。

**验证方式**：两个生成器各自跑了10000次随机试验（不是随便测几次），确认**零失败**——每一次生成出来的所有中间数字和最终答案都是干净的正整数，没有漏网的浮点数或除不尽的情况。

### 互动作答方式

牛吃草：一个加减号的数字调整器（要么调"几头牛"要么调"几天"，看题目问哪个），点确认送出答案。

浓度问题：一个"加水"的滑杆，拖动的时候画面上会即时显示"现在浓度是多少%"，滑到目标浓度会有对勾提示，点确认送出。

两个都是跟鸡兔同笼、相遇问题一样的"试着调整、看即时反馈"风格，不是让学生自己在草稿纸上算完再选答案。

## 修了"编辑时标记的位置，玩的时候跑位"这个bug——四个模块都中招

### 根本原因

设计器的画布用 `ctx.drawImage(img, 0, 0, 画布宽, 画布高)` 把背景图画上去——这个方法**不管原图比例是多少，一律拉伸到刚好塞满整个画布**，不会裁切。所以设计器里标记的每一个坐标点，是相对于"整张图被拉伸铺满"这个前提算出来的。

但游戏实际玩的时候，背景图是用 CSS 的 `background-size: cover`（或者 `<img>` 标签的 `object-cover`）显示的——这个是**裁切填满、保持原图比例**，不是拉伸。如果上传的图片原始比例不是刚好11:7（画布固定比例），"cover"就会把超出的部分裁掉，裁掉多少、从哪边裁，取决于原图实际比例跟目标比例差多少。

**这两种缩放方式对同一张图片的处理结果不一样**——只要原图比例不是刚好11:7，画面上"背景图实际显示出来的样子"在设计器跟游戏里就会不同，用同一个归一化坐标（比如"图片20%宽、30%高的位置"）去对应，落到的实际画面位置自然就对不上了。这不是"随机跑位"，是有明确原因、必然发生的系统性偏差——只要上传的图片比例跟11:7有落差，就一定会跑位，偏差幅度取决于比例差多少。

### 修了哪几个地方

一共查到并修正了**四个游戏引擎**里同样的问题：
- **数独**（`SudokuGame.tsx`）——就是这次截图报的那个，空格输入框跟着背景图的实际数字格错位
- **点点数数**自定义场景（`CountingGame.tsx`）
- **应用题**自定义题目（`WordProblemGame.tsx`，上次刚做的那个新功能）
- **专注力点数字**自定义模式（`FocusTapGame.tsx`）——这个是用 `<img>` 标签的 `object-cover` 表现出同样的问题，不是CSS背景图，找的时候容易漏掉，这次也一并抓出来修了

顺带把 **Memory配对**的自定义背景（`MemoryGame.tsx`）也改了——这个虽然没有坐标定位的问题（卡片位置是随机洗牌的，不依赖背景图的具体坐标），但同样的裁切/拉伸不一致会让背景"看起来"跟设计器预览的不一样，一起修掉保持一致。

**统一改法**：把这五个地方全部从"裁切填满"（`cover`）改成"拉伸填满"（`100% 100%` 或者 `<img>` 的 `object-fill`），跟设计器画布的行为对齐——这样不管上传的图片原始比例是多少，设计器里标记的位置，跟游戏里显示出来的位置，永远是同一个坐标系，不会再跑位。

## LogiVerse 教育内容架构 v1.0——Programme → Subject → Topic → Activity

这是这次对话里最大的一次架构决定。根据你上传的架构文件，建立统一的四层内容分类体系。**这次只完成了后端——数据库、API全部做完并测试过；前端管理界面还没做，下一轮继续。**

### 处理原则：加一层，不是打掉重建

这个项目累积了27个migration、大量互相依赖的表——`course_levels`、`exercise_categories`、`exercise_groups`、编号系统、素材分类、学生管理……如果现在把这些全部推翻重建成符合新架构命名的全新表，风险和工作量都远超一次能安全交付的范围，而且会牵动这次对话里几乎每一个已经做完并测试过的功能。

所以这次的做法，延续"关卡→习题"当初的处理方式——**新架构是加上去的一层概念，不是物理表的重建**：

- `edu.exercise_categories`（原本叫"习题大种类"）**概念上直接升级成 Topic**——物理表没有改名（外键牵动 course_levels、exercise_groups、exercise_number_counters、编号系统全部依赖这张表，改名风险远大于收益），但加了 `subject_id` 挂到新的 Subject 底下
- `edu.course_levels`（"习题"）**概念上升级成 Activity**——加了一整套新属性栏位（下面详列）
- 新建两张表：`edu.programmes`（课程体系）、`edu.subjects`（学习领域）

**`edu.courses`（课程）和 `edu.lessons`（课时/教案）完全没有变动**——这两个不属于新架构要处理的范畴。新架构回答的是"这个活动教的是什么"（分类问题），courses/lessons 回答的是"这些活动怎么组织成一套教学流程给学生"（教学编排问题），是两个不同维度，不是互相替代的关系。

### 数据库新增内容

**Programme（课程体系）**——`edu.programmes`：code、中英文名称、描述。

**Subject（学习领域）**——`edu.subjects`：挂在某个 Programme 底下，code+programme_id 组合唯一。

**Topic（学习主题）**——沿用 `edu.exercise_categories`，加了 `subject_id` 外键。

**Activity（学习活动）属性**——`edu.course_levels` 新增：
- `activity_type`（活动类型）：interactive / game / exercise / worksheet / assessment / simulation
- `teaching_modes`（教学模式，**多选**）：classroom / self_guided / discovery / homework / assessment / revision——架构文件里特别注明"教学模式属于属性，不是分类"，所以做成可以同时勾选多个的阵列，不是单选
- `difficulty`（难度，**新的五级标准**）：starter / easy / medium / hard / expert——这是全模块通用的新栏位，跟数独原本自己的 `difficulty`（easy/medium/hard/custom）是两个独立栏位，没有合并（合并需要处理数独已有数据的转换，风险跟收益不成比例，这次先并存）
- `age_group_min` / `age_group_max`（年龄段）
- `duration_minutes`（预计时间）
- `learning_outcomes`（学习成果，自由文字）
- `skills_developed`（培养能力，**不限3个**——这个刻意跟标签系统的3个上限分开处理，一个活动同时培养好几种能力是很正常的事，不应该被"标签最多3个"这个规则限制住）
- `language`（语言）：跟素材库的语言栏位用同一套（universal/zh/en）
- `tags`（标签，最多3个）：延续素材库标签系统的同一套规则

## 建 Activity 必须先确定 Programme → Subject → Topic——逻辑修正

你指出的问题是对的：之前"加 Activity"表单里选分类那块，只是一个扁平的 Topic 下拉框，埋在表单深处，是选填的，而且完全没有先选 Programme 再选 Subject 这个层级关系。这跟 LogiVerse Education Taxonomy v1.0 那份架构文件定义的逻辑不符——一个 Activity 应该先确定它属于哪个 Programme、哪个 Subject，才能确定它属于哪个 Topic。

### 改了什么

**表单最显眼的位置**（紫色边框标出，带红色星号）现在是一个真正的三层级联选择器：先选 Programme，选了才能选 Subject（下拉框选项跟着 Programme 变），选了 Subject 才能选 Topic（选项跟着 Subject 变）。选上一层清空重选下一层，避免出现"选了A课程体系底下的Topic，但画面上Subject栏位显示的是另一个课程体系底下的东西"这种不一致状态。

**双向自动对齐**：不管 Topic 是设计者自己在下拉框选的，还是靠"选了模块类型自动带出对应Topic"这个原有的便利功能带出来的，只要 Topic 一确定，画面上的 Subject、Programme 两个栏位都会自动跟着对齐，不会出现"Topic选好了，但上面两层还空着"的画面。

### 新建强制要求，编辑不强制——这是刻意的权衡

**新建 Activity 时**，前端和后端都会挡下"没选 Topic 就想保存"这件事——用 curl 直接跳过前端调 API 测试过，后端正确拒绝，报错信息写清楚原因，不是生硬的400。

**编辑已有 Activity 时，不会强制要求**。原因：这几轮测试下来，已经有不少更早期建立的、还没来得及分类的老 Activity。如果编辑也强制要求先补 Topic，会变成"只是想改个错字，却被逼着先做分类"这种不合理的阻塞。所以编辑的时候：已经有 Topic 的 Activity，只要这次编辑没有主动去改这个栏位，后端会保留原值不清空（改成用 `COALESCE` 而不是直接覆盖）；本来就没有 Topic 的老 Activity，编辑其他内容一样能正常保存，不会被卡住。

### 实测过四种情况

1. 新建时不带 Topic → 后端正确拒绝，报错信息清楚
2. 新建时带 Topic → 成功
3. 编辑一个本来就没有 Topic 的老 Activity，不特意去补 → 保存成功，Topic 依然是空的（没有被强迫设定，也没有报错卡住）
4. 编辑一个已经有 Topic 的 Activity，这次编辑没有碰这个栏位 → 保存成功，Topic 原封不动保留（没有被意外清空）

四种情况都用 API 直接测试过，全部符合预期，测完把测试数据清理干净。

## 发现并修了一个之前没抓到的漏洞——"上传后马上用"这条路，图片其实还是整份塞进习题设定里

你问"物件图片和背景图片还是存在数据库吗"，认真查了一遍代码才发现答案不是简单的"不是"——**要分情况**，而且揪出了一个之前几轮做"素材库改存URL"的时候没发现的漏洞。

### 三条路径，只有一条是干净的

设计习题时透过"选素材"弹窗（AssetPicker）选图片，实际上有三种操作方式：

1. **从素材库选一张已经存在的图片**——干净，习题设定里存的是URL
2. **弹窗里直接上传新图片、马上使用**——图片确实有正确存进素材库（磁盘+URL），**但"马上用"这一步，代码里错误地把上传当下读到的完整base64内容传给了习题设定，不是刚存好的那个URL**
3. **弹窗里用"图片编辑工具"现画/现合成、马上使用**——同样的错误

也就是说，2和3这两条路径，虽然素材库那一份是干净的（磁盘+URL），但**习题自己的设定（比如迷宫的背景图栏位）却还是整张图重新塞了一次**——同一张图片实质上被存了两份，一份在素材库、一份直接埋在习题的设定资料里，完全没有达到"数据库只存网址"这个目标。

### 怎么修的

后端：`createAsset` 现在会把刚存好的那个网址也一起回传（之前只回传id、名称这些，没有回传网址本身），前端不用再另外拉一次才知道网址是什么。

前端：AssetPicker 的"上传新图片"跟 SceneEditor 的"存到素材库"这两个存档流程，都改成用后端回传的那个网址去通知调用它的模块（比如迷宫的背景图选择器），不再传本地读到的原始图片内容。

### 实测过

## 新增"设置"页面——素材储存网址现在能在界面上改，不用改文件、不用重启服务器

### 问题

之前素材储存网址（`ASSET_BASE_URL`）只写在后端的 `.env` 文件里，是一个环境变量——环境变量的特性是"程序启动的时候读一次就固定住"，想改就得手动编辑服务器上的文件，还要重启整个后端服务才会生效。这对会写代码的人来说还好，但对业者来说，"要改一个网址还得找工程师上服务器改文件重启"这件事完全不合理。

### 解法：把这个值从环境变量搬进数据库

新建了一张很小的通用设置表 `edu.system_settings`（key-value 结构，不是只为了这一个设置量身订做的表，以后有别的系统层级设置也能用同一张表存，不用每加一个设置就建一张新表）。后端现在改成每次要用这个网址的时候去数据库查（带10秒缓存，不会因为这样就变成每次上传素材都多打一次数据库），改了之后**下一次请求就生效**，不需要重启。原本 `.env` 里的 `ASSET_BASE_URL` 还留着当"数据库里还没设过的时候"的备用默认值——现有的部署不会因为这次改动而出问题，行为跟以前一模一样，除非有人真的透过新的设置页面去改它。

### 新增设置页面（仅业者可见）

导航栏新增"设置"，目前只有"素材储存网址"这一项，能看到目前的值、能直接改、存档按钮在没有改动的时候会自动disable（避免手滑重复送出一样的东西）。页面上写清楚了这个网址是干什么用的、改了会影响什么（只影响之后新上传的素材，已经上传过的素材网址不会跟着变，因为那是当时就已经存进资料库的固定值）。

### 实测过

**最关键的一步**——改了这个设置之后，**没有重启后端服务器**，直接上传一张新素材，确认回传的网址真的用了刚改的新网址，不是旧的那个。这证明"不用重启就生效"这件事是真的做到了，不是我随便讲讲。另外也测了：默认值正确读到环境变量、传一个格式不对的网址（没有 http/https 开头）会被正确拒绝、存的时候会自动把网址结尾多余的斜杠去掉（避免以后拼出 `//uploads` 这种重复斜杠的网址）。测完把设置改回本机开发用的网址，也清理了测试用的素材。

### 过程中发现并修好一个逻辑缺口

测试"先建立未分类的Activity，之后编辑补上Topic"这个新流程时，发现补上Topic之后编号（如 CT-10003）并没有跟着自动生成——但弹窗里的说明文字明明写着"选了 Topic 之后保存时会自动生成编号"。查了原本的代码注释才发现：`updateLevel` 之前刻意设计成"编辑不会重新生成编号"，原意是避免"只是想改个错字，编号却被意外打乱"，但这个设计没有考虑到"从来没有过编号、这是第一次补上分类"这种全新情况——这两种情况该有不同的行为，原本的逻辑把它们混在一起处理了。

修法：只有当这个 Activity **从来没有编号过**、而且**这次编辑带上了 category_id**，才会生成编号；已经有编号的 Activity，不管怎么编辑都不会被重新生成/打乱，原本的保护逻辑照样保留。

**按主题汇总**（新增后端接口）——把同一个孩子所有打过的 Activity，按 Topic（比如"数独"、"点点数数"）汇总起来，算出每个主题的平均分数、完成率、总共打了几关几次，**弱的主题排在前面**，一眼看出孩子哪里需要加强。算平均分的时候，同一关打了好几次，只取**最好的一次**成绩去算——不然一个孩子为了破关反复重打5次，看起来会比一次就答对的孩子表现"更差"，这样不合理。

### 过程中抓到一个真实的SQL bug

## 新游戏模块：连线配对 — 完整交付（数据库+后端+设计器+游戏引擎+播放页面）

### 答案隐藏——这次最花心思的地方

如果直接把配对关系原样传给前端，打开浏览器开发者工具就能一眼看出哪个连哪个（左边第N项跟右边第N项数据结构上直接对应，纯视觉打乱骗不了人）。这次的做法：

- 左栏：保持原始顺序传给学生——左边的顺序本身不是秘密
- 右栏：内容打乱顺序传，每个项目给一个跟原始配对顺序完全无关的临时编号，**不带任何能推回正确配对的字段**
- 学生连完线，把"左边第几项连到了什么内容"（不是编号，是实际内容）送回来
- 后端拿数据库里原始的配对表重新核对，不信任前端送来的任何编号

跟数独"答案永远不下发、检查在服务器做"是同一个原则，这次多解决了一个"连打乱顺序都不能泄漏配对关系"的额外问题。

### 最关键的问题：手机上原本完全没办法导航

查代码发现，左侧导航栏原本是 `hidden md:block`——意思是**屏幕宽度低于768px（几乎所有手机）导航栏会直接消失，而且没有任何替代方案**。也就是说这套系统现在这个状态，用手机打开，除了首页Logo那个连结，哪里都点不到。这是移动适配里优先级最高、必须先解决的问题，不然其他细节修再多也没用。

修法：重写了 `AppLayout.tsx`，加了一个只在小屏幕出现的汉堡菜单按钮，点开会有一个下拉面板，里面的连结清单跟桌面版侧边栏共用同一份数组（不是分开各写一份，避免两边改一边忘了改另一边、之后某个角色在手机上跟电脑上看到的选项对不起来）。切换页面会自动把菜单收起来。同时给最外层容器和主内容区加了 `env(safe-area-inset-top/bottom)` 的留白，这样在有瀏海或底部手势条的iPhone上，内容不会被系统UI挡住一截——这个问题只有包成App之后才会真的发生，纯网页浏览器场景不会遇到。

### iOS 的"点输入框自动放大画面"问题

这是iOS Safari/WKWebView（Capacitor包出来的App用的就是这个引擎）一个有明确记录的行为：文字大小低于16px的输入框，被点击时系统会强制把整个画面放大，而且不会自动缩回去。查了一下，共用的 `Input`、`Textarea` 组件，还有家长仪表板里一个筛选用的下拉选单，字体都是14px（`text-sm`）。改成小屏幕16px、桌面维持14px（`text-base sm:text-sm`），两边都兼顾。因为 `Input`/`Textarea` 是全站共用组件，这个修法会连带修好整个系统所有表单，不只是学生家长这个范围。

### 触控热区太小的地方

给4-12岁小朋友用的东西，手指精准度比大人差，太小的按钮容易点不中。查到两个明显偏小的：连线配对游戏里"清除这条线"的✕按钮（20px，改成28px）、填色游戏的调色盘颜色圆点（32px，改成44px——业界建议的最小触控热区就是44px，这个是核心互动，特意补到位）。
